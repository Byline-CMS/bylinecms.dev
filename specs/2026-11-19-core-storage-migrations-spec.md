# Core storage installation and upgrades

Companions:

- [Implementation plan](./2026-11-19-core-storage-migrations-plan.md)
- [PostgreSQL host journal conflict, issue 105](https://github.com/Byline-CMS/bylinecms.dev/issues/105)

**Status** · Operator contract for review, including the proposed scheduled-update policy, 2026-11-19.

## How the migration works

You use the CLI for provisioning and the selected database adapter for core storage migrations. These commands describe the proposed interface. The cutover checkpoint includes native step 0015 on PostgreSQL or 0010 on MySQL.

| Situation | What you do | What changes and what you see on failure |
|---|---|---|
| Fresh dedicated database | Run the usual `byline init` or `byline setup` flow with the selected dialect. | The CLI inspects the target before provisioning. The adapter installs its frozen baseline, records one checkpoint in `byline_core_migrations`, then applies subsequent numbered steps. A provisioning failure can leave a database or role. Status distinguishes this from a completed storage install. Seeding follows storage success. |
| PostgreSQL host already using Drizzle | Set the existing PostgreSQL connection environment variable and run `byline setup --database postgres --existing-database --apply`. Coordinate a quiet period for host DDL. | The adapter checks the target on the supplied connection, creates core objects in `public` and writes its own journal. A conflicting table, index, type or missing prerequisite stops installation with the object and namespace. The host keeps its role, grants, data and migration history. |
| Existing Byline installation | Take a recoverable backup, record the deployed release and manual upgrade evidence, fence writers and workers, then run `byline storage status`. For a verified checkpoint run `byline storage adopt`, then check status again. | Adoption verifies the live schema and data and records a single row marked `adopted`. A mismatch reports the failed check before recording a checkpoint. You can retain a previous Drizzle journal, including one shared with the host. |
| Next upgrade | With the target release's CLI, inspect status, fence traffic and workers and run `byline storage migrate`. | Each successful step advances the journal once. PostgreSQL rolls back a failed transactional step. MySQL reports the step and which DDL has already committed. Rerun with the same release after checking status. Keep the fence until the new application passes startup checks. |
| Scheduled update | Configure the deployment to run `byline storage migrate --online-only` with the target release before promoting new instances. | The command applies an eligible set of proven online steps. If any pending step requires a fence, it exits before applying any of them and the current deployment remains in service. A database failure during execution stops promotion and reports the last durable step. |
| Application startup | Start the matching application using its ordinary runtime credentials. | A read-only schema check verifies the installed version and journal integrity. A missing, pending, partial or incompatible schema (including a newer one outside the supported range) stops startup before document traffic or workers and reports the operator action. |

## Cutover baseline and numbered history

Use the v6.13.4 storage definitions as the cutover target. At the planning base the adapter baselines and legacy SQL directories match that tag. Freeze one new authoritative SQL baseline per adapter from its current `0000_*.sql`. PostgreSQL includes the cumulative effects through native script 0015 and begins the next numbered step at 0016. MySQL includes effects through 0010 and begins at 0011. An accepted installation has exactly one starting row for its dialect. The row attests to the verified checkpoint. It makes no assertion about individual historical executions. The host's Drizzle timestamps, CLI release numbers and future Drizzle development squashes play no part in ordering.

Keep the baseline bytes and every subsequently released migration immutable. Each manifest entry identifies the dialect, integer version, stable name and SHA-256 of its packaged SQL. The manifest also records each step's classification (`online` or `fenced`) and `compatible_from`, the oldest consecutively supported **schema contract version** for readers and writers. The baseline uses fenced/0015 or fenced/0010 respectively. Persist both fields in the journal from its first format. Include stage definitions, classifications, compatibility floors and pre/postcondition contracts in the immutable release inventory. Enforce consecutive unique versions at build and at discovery. Fresh installs always run the frozen baseline and the same suffix an adopted installation would run. There is no per-release re-baselining. Preserve release-tagged legacy instructions and SQL for installations below the checkpoint. Keep Drizzle's schema definitions, development diff generation and query/transaction APIs. Search and analytics retain separate runners, locks and history.

At cutover, close each switched adapter's hand-applied `sql/` directory at its stated endpoint and update its README. Put the new frozen baseline, manifest and numbered suffix in `packages/db-<dialect>/migrations/`. The old PostgreSQL ownership-guard test continues to check the legacy scripts through 0015. A separate gate checks all runner SQL for forbidden ownership reassignment, grants and legacy blanket guards. Compare both histories with the prior released tag. When an unjournaled database has effects of a known later migration, status identifies those effects and refuses adoption. Restore a verified checkpoint or rehearse an object-scoped reversion that preserves content, then adopt and migrate. Never re-run that step over unexplained effects.

The journal lives at `public.byline_core_migrations` or in the selected MySQL database. Give it a recognizable versioned definition, an integer primary key on version, operation origin (installed, adopted or migrated), artifact digest, state (applying or applied) and completion timestamp. An adopted row uses the frozen checkpoint digest as its contract identifier. Keep the installation identifier stable across all rows of an installation; compare it during direct/runtime target checks. Only completed rows count as applied. Validate the journal's own table shape, baseline identity, expected sequence, origin/state combinations and known digests before using it. Reject holes, an unknown future version, altered history, an invalid applying row or an unexpected object occupying its name. A higher maximum alone proves nothing.

## Status and adoption evidence

All storage commands accept `--database postgres|mysql`, honor persisted adapter selection and reject conflicts. Resolve the dialect's configured connection environment variable, retaining driver connection options and redacting credentials. Status is read-only, including on an empty target. Report the dialect, target database/schema, expected and observed versions, pending steps, failed checks and next command. Distinguish missing/empty, unrelated or provider-only, recognized unjournaled core, partial/unrecognized core, current, pending, interrupted, newer, corrupt and inaccessible. Report inadequate visibility as an inspection failure. Ordinary status should be inexpensive on a journaled installation. Deep inspection of an unjournaled candidate can scan content and should be identified as such.

Ship a dialect-specific catalog contract derived from a clean cutover database and tested against a representative native-upgraded database. Use logical, normalized metadata so role names, catalog IDs and server formatting do not determine compatibility. Compare actual object kinds, column types/length/precision, collation, nullability, defaults, generated expressions, keys and ordered index definitions, uniqueness, foreign-key endpoints/actions, validated or enforced check expressions and the semantics of both current-version views. Check incompatible additions on core tables such as extra mandatory columns without defaults, conflicting triggers or constraints. Explicitly document and fixture any equivalent legacy name/definition accepted. An unknown difference affecting writes or visibility requires diagnosis. Unrelated host objects, search and analytics tables fall outside the checkpoint contract.

Require read-only data checks corresponding to historical migrations. In particular:

- Documents have a populated source locale and a positive, safe-integer revision. The two revision columns and the enforced checks must pass the existing revision-schema validation. Armed publication schedules require a valid authorization revision. Legacy unverified schedules must have passed through reconfirmation or invalidation.
- Verify historical path liveness against the live/deleted versions using the conditions in the path-liveness upgrade. Check the stored generated `alive` expression and the four-column live-path unique key.
- Verify that the historical version-locale backfill has supplied the required ledger coverage for applicable versions. Derive coverage from localized stored field paths and the document's source locale using the adapter's backfill semantics, including the `all` case for versions without localized paths. Account for documented re-anchoring or other legitimate post-upgrade states in fixtures before enabling this predicate. The tagged version-locale backfill is the remedy for verified missing historical coverage. Each blocking predicate must have a documented remediation tested on representative data, including fenced restore where the lost evidence cannot be reconstructed.
- Check the passkey/session tables, keys and constraints and both nullable stored-file validator columns with their declared lengths. Unknown file identity can legitimately remain null. The operator can supply migration logs and backup provenance for history that current data cannot establish.

Run status against a restored copy first. For an older deployment, use the target tag's native upgrade instructions and required application backfills to reach this checkpoint. Historical PostgreSQL scripts contain transaction boundaries and some reassign ownership across `public`. In a shared database, rehearse a separately inspected, object-scoped remediation for each missing effect. A blanket legacy replay under a privileged account can alter host objects. Report individual discrepancies and keep adoption blocked until a supported shape and required data are present. A release string, latest validator column, prefix match, operator assertion or Drizzle row alone cannot establish this evidence.

Under the core lock, adoption repeats the inspection with old writers and workers fenced. It writes only the journal on success. A second adoption of the same checkpoint is a verified no-op. A journal with later migrations directs the operator to status. Adoption never fills fabricated history, silently repairs schema or runs pending migrations. Retain the original evidence alongside the deployment record.

## Install and collision rules

Dedicated provisioning remains the default. Preserve occupied-target refusal before role/database changes, sticky dialect selection, seed options, and the existing destructive-reset confirmation for dedicated targets. A rerun of the **adapter** install on a verified completed installation is a no-op at the same target version. The outer dedicated CLI still protects occupied databases. Status/migrate are available after a committed baseline, including when a later seed phase fails.

The opt-in existing-database setup initially supports PostgreSQL. Its target is `public`. Reject a connection whose effective creation schema differs, or whose explicit search path requests another application schema, before applying SQL. Accept the standard default resolving to `public`, then pin the session to the supported path; quote and qualify catalog references. Reject temporary-schema shadowing. It bypasses administrative connection prompts, provisioning, password rotation, ownership transfer and grants. Reject reset flags with this mode before any phase or completion-state shortcut. Validate the actual connected database, migration-role privileges, `public` schema, installed prerequisites (including the CLI's pgcrypto prerequisite), and intended target before mutation. Later seeding uses the configured application connection and existing seed choices. An unjournaled core candidate receives an adoption diagnosis. Provider-only or host-only targets are eligible after collision checks. A standalone status or migrate operation never provisions a database.

Preflight **all names** the SQL will claim, including the journal and unprefixed indexes. Derive and verify the inventory from executing the packaged SQL on an empty fixture. PostgreSQL relations share a schema namespace across tables, indexes, sequences, views and other relation kinds. Check type namespace conflicts including table row types, constraint-backed indexes and implicit names, and constraint names in their actual namespace. Use qualified catalog queries and pin a trusted search path on the migration session so the baseline and both views bind to the intended objects. Require the host to reserve those names and serialize its own concurrent DDL during install. The core lock coordinates Byline processes only. A racing PostgreSQL name conflict aborts the transaction. Preserve existing names for this release. Renames would require an independent numbered upgrade.

Core baseline and upgrade SQL never grants permissions or changes object ownership. In dedicated PostgreSQL setup the provisioner connects to apply the baseline as the application role. In a split-role deployment the migration role owns the objects it creates. The operator grants runtime access on existing core objects and arranges grants on new ones. PostgreSQL default privileges must be set for the actual creating role and namespace, with separate DML grants limited to content objects and SELECT on the journal. A shared schema may need explicit object-specific grants per step. MySQL operators apply equivalent grants on the named tables/views. Verify access as the runtime identity before lifting the fence. The storage commands use the selected connection for the operation; execute a separate invocation with migration credentials for DDL, then check status and start the application with runtime credentials. Neither credentials nor grants are copied from one invocation to another.

For MySQL, install only into the selected database, check table/view names with the server's case rules, table-scoped indexes, database-scoped constraint symbols where applicable, engine capabilities, expected charset/collations and view security/definer access. Initially retain dedicated-only setup for MySQL. The recovery and adoption contract still checks exact names and shapes before accepting any existing object.

## Locking, interruption and rollback

Use one physical connection from lock acquisition through final verification and release. PostgreSQL uses a reserved database-local advisory key distinct from search and analytics, with a bounded acquisition timeout. Pin the schema for execution, re-inspect under lock and create the journal, execute the baseline, verify postconditions and insert the first applied row in one transaction. Run each later step including its row in its own transaction. For this format reject transaction-control statements and operations requiring nontransactional DDL. On failure roll back the current step. Previously committed steps remain visible. If commit acknowledgement is lost, reconnect and inspect the recorded version and digest before retrying. Release or discard the physical connection on all exits.

MySQL uses a bounded `GET_LOCK` on a deterministic database-specific name within the server length limit. Check the actual lock result and release on the same session. Preflight support for enforced CHECK constraints as well as the existing engine/version check. Create an identifiable journal table, then commit a durable `applying` row **before the first baseline or upgrade statement**. Only one highest pending row is valid. If interrupted after journal creation but before this first row, a correctly shaped empty journal is a bootstrap interruption. Repeat the original operation, checking the entire target again. Do not infer completion from an empty journal. Adoption checks the full candidate before journal creation, and repeats it on this recovery path.

Define each MySQL migration, including the baseline, as ordered stages with exact before/after predicates. For example, verify a table's columns and keys before proceeding to a separate FK stage. After a disconnect, compare each completed stage with its expected shape at the observed prefix. Resume from the first definitely unapplied stage. If DDL finished and only completion logging was lost, recheck all final postconditions and mark the existing row applied once. For data backfills use one transactional data change with its progress update, or a proved idempotent predicate. Never infer success from an already-existing table name. A non-prefix, incompatible or ambiguous state leaves the row applying and reports the version, stage, object, expected and observed definitions. Require a rehearsed object-scoped repair or fenced restore. Startup refuses every incomplete state. Fault fixtures must interrupt before DDL, between stages and after all DDL but before the completion update.

On a lock timeout report the dialect, database, lock identifier, wait duration and a retry action. Use PostgreSQL lock/activity metadata for the advisory key or MySQL `IS_USED_LOCK()` and visible process metadata to identify the holder when allowed. Redact SQL text and credentials. Restricted visibility reports “holder unavailable”. A session list cannot prove fencing: pools can reconnect and idle sessions can be harmless. The operator controls the fence; online connection counts do not gate migration.

On both engines, fence every writer, worker and schema-changing host process for initial adoption and for the ordinary operator-led migration procedure. The release-phase online path below is the supported exception for upgrades with live application writers. Keep a restore point covering affected data and journals. Code-only rollback is possible when the previous application demonstrably supports the database's current version and write contract. An interrupted PostgreSQL step leaves its predecessor usable only if that compatibility holds. For an incompatible committed upgrade, fence, restore the database and matching code together, and verify host consistency before reopening. Shared-database recovery must coordinate the host's recovery point and any intervening host writes.

## Startup and rollout

Supply status, adoption and explicit migration before shipping mandatory journal checks on a switched dialect. During that transition the existing adapter startup checks still apply. A dialect may ship these tools ahead of enforcement only while its package still targets the frozen checkpoint. The first release containing a post-checkpoint step must enforce its mandatory startup check before any new code uses that step. Never ship a writer that requires new SQL while startup accepts an unadopted checkpoint. At cutover the compatibility floor equals the checkpoint, so only that version is supported. Later a verified online step may allow more than one application schema version under the rules below. Startup never applies even additive steps. The operator uses status/adopt for missing history, migrate for known pending steps, the matching newer release for a future schema outside the supported window, and the recovery procedure for partial states.

Run the official adapter's read-only compatibility check at the start of core database validation, before boot backfills, syncs, workers or traffic. Preserve the existing `assertDocumentRevisionCapability` and dialect-specific checks. Make the new capability explicit for switched built-in adapters while preserving third-party adapter compatibility. Cover any standalone worker entry that can start outside core initialization. Startup checks journal structure and rows, the supported compatibility range, runtime access and existing targeted engine/revision invariants. Full catalog comparisons, view definition checks and content scans belong to deep status and adoption. On PostgreSQL the runtime needs CONNECT, USAGE on the target schema, SELECT on the journal and read views, ordinary content table DML and sequence usage where used. On MySQL it needs SELECT on the journal and read views, ordinary content table DML and the resulting metadata visibility for targeted checks. Deep inspection additionally needs access to definitions including MySQL SHOW VIEW. Report a missing privilege or incomplete metadata visibility as an inspection failure naming the object and needed access. Test startup and ordinary reads/writes as a non-owner runtime role without DDL or journal writes on each engine. Search auto-migration and analytics migration can perform DDL when configured at boot. Provision those independent journals separately when using restricted runtime credentials. Migration credentials alone need DDL and journal writes. Other boot work may perform application writes. Restricting journal-check permissions must not disable schema validation.

## Scheduled updates with live writers

**Recommended deployment policy.** Run `byline storage migrate --online-only` once in the target release's predeploy job, after staging the new packages and before routing traffic to them. Keep the runtime connection and privileges separate. Supply `BYLINE_MIGRATION_DATABASE_URL` for a direct, DDL-capable connection to the selected database. Require dialect, database and operator-configured deployment target to agree; runtime and direct endpoint hostnames may differ for the same database. On PostgreSQL verify the target identity against the runtime connection (for example a consistent database-specific installation identifier stored in the journal at creation, carried over on restore, plus database name); define the same check for MySQL. A clone shares the source identifier, so the deployment configuration must pair direct and runtime endpoints for the intended environment. Status reports the effective target without credentials. If no direct connection is supplied, or the driver cannot retain a single physical session, stop. A transaction/statement pooler is unsupported. Two equal backend PID samples cannot prove a direct connection. Require a documented direct/session endpoint verified by the deployment owner. Limit DDL credentials to the job.

Under the core lock, re-read the journal and examine the **entire** pending set before the first write. Require a clean, adopted or installed database, a matching deployment target and package identity, an intact known history, and online eligibility for every step across the declared deployed writer/worker versions. The release job passes a repeatable `--deployed-adapter-version <exact-release>` for the versions still taking traffic or running workers, from the deployment inventory. The target manifest maps tested release identities to their schema contracts. An omitted, unknown or untested active release blocks automatic advancement. A current target with no pending work needs no fleet declaration. If compatibility cannot be established, any step is fenced, or the database is empty, unadopted, ahead of the command, applying or corrupt, exit nonzero with the operator action. A compatible current target exits successfully without a journal write. Never install, adopt, repair or acknowledge an interruption in automatic mode. Keep versions and target details in deployment logs and stop promotion on failure.

Whole-set eligibility is atomic with respect to the Byline lock. Execution keeps the per-step durability rules of each dialect. If the second eligible step fails, the first may remain committed. PostgreSQL rolls back the failing transaction; re-inspect before retry. On MySQL the last step can be `applying` with durable partial DDL. Keep the deployment stopped and run supervised status/recovery. An automatic MySQL run can temporarily block new instance readiness; enable it only where the deployment tolerates this, after rehearsing the interruption points. Existing healthy instances need compatible intermediate schemas throughout.

**Which steps qualify.** Default every new step to fenced. An online step is an additive change with a measured lock/statement budget, idempotent recovery and recorded evidence that the prior release's real reader, writer and workers operate correctly throughout. Test concurrent old/new writes on representative data and exercise bounded contention/abort on the supported engine. Do not infer eligibility from an SQL verb. A fast metadata operation on one server or table size may rewrite another table. A backfill must be safe beside ongoing writes and fit the supported single-step transaction or durable stage model. Destructive changes, tighter invariants, historical authorization/revision changes and operations with unbounded locks require a fence. On MySQL also require exact pre/postconditions and compatibility for each committed prefix, and enforce explicit online DDL algorithm/lock requirements where applicable; reject fallback to a blocking algorithm.

**Compatibility evidence and startup.** Every online step must support at least its predecessor. Its declared floor may admit additional older versions only when the release tests every admitted contract, including the intervening states during rolling deployment. Floors never decrease; a fenced step raises the floor to its own version. A prior version's successful test at one earlier migration cannot establish transitive compatibility. Run representative N−1 release reads, writes, workflow and worker operations against the new schema and repeat for any earlier contract covered by the floor. Coordinate the deployed fleet at the job boundary; a startup check cannot revoke an already-running writer.

A runtime requires its own version to be installed. Validate the journal definition and known rows against local digests, classification and floors. For a higher contiguous suffix in the supported journal format, admit it only if every row is applied, structurally valid, classed online and has a monotonic floor at or below the runtime's required version. Verify each known row fully. For unknown rows the runtime necessarily trusts the authorized migration role's recorded compatibility declaration; it cannot independently check SQL it does not have. Reject unknown format, gaps, applying rows, impossible floors, unknown classifications or a fenced suffix. An exact-version cutover and an operator fence remain the default where prior releases lack this compatibility protocol. Verify the journal writer privilege is unavailable to ordinary split-role runtime accounts. Dedicated installations that use the same owner for both roles trust that owner.

**Startup-only hosts.** Keep automatic DDL out of application startup on both engines for this design. For installations without a dedicated release phase, provide a one-shot launcher/init job using the direct connection that completes before the new application starts. This gives scheduled updates the same command, failure semantics and credential separation without a per-instance migration election or a race on serverless cold starts. Retain supervised, fenced adoption even when the operator believes every writer runs the checkpoint release: a schema inspection cannot identify every external worker or guarantee consistent historical evidence across concurrent writes. The one-time cutover buys automatic handling of later qualified steps. For rehearsal, a restored copy or provider-managed database branch can run the same job with its own connection pair.

## Distribution and proof

Publish a Node-only `@byline/db-<dialect>/migrations` entry plus immutable raw SQL and a manifest in the adapter tarball. Resolve artifacts relative to the installed adapter module. Support direct inspection and offline deployment of those bytes. For a supervised SQL-only baseline on an empty or preflighted PostgreSQL target, an operator may execute the packaged SQL under the same schema/role and transaction controls, then run status and explicit adoption. This records adopted origin. Document the complete preflight, lock/fence and post-verification procedure before supporting this alternative.

The CLI's database phase currently precedes host dependency installation. Give the CLI an exact runtime dependency on each switched adapter (workspace dependency published as an exact version) and lazy-load only the selected migrations entry from the CLI's package context. This increases the CLI installation footprint but preserves existing phase order, exact host adapter selection and a consistent implementation when no host config exists. Check package/manifest identity before provisioning. In a host project resolve the installed adapter package.json from the host root and report both CLI-owned and host adapter versions. Status remains available on a mismatch. Refuse a mutating storage operation on a mismatch; for a deliberate fenced deployment permit `--target-adapter-version <exact-version>` only when it matches the CLI-owned adapter, and echo the deployment target and required matching application before proceeding. Refuse unresolved declared host dependencies for upgrades until installed; new CLI provisioning before the host dependency phase uses the CLI's exact dependency. An operator may run storage commands standalone from a deployment tool directory using the target release. Preserve the MySQL bundled CLI baseline until MySQL switches. Remove duplicate per-dialect baseline sync and packaging requirements as each replacement lands. Do not import the host's server config to find or execute migrations.

Build and unpack real release-form tarballs in an isolated consumer with no monorepo source lookup or registry fallback for the packages under test. Exercise status/install/migrate against the repository's isolated databases, validate SQL digests, and compare fresh and upgraded catalogs, content reads/writes, workflow state and unaffected host history. Keep released native scripts immutable, extend the existing release-history gate to new artifacts and ensure every schema change has a numbered step. Switch test bootstrap to the same adapter runner, preserve journals during fixture cleanup, and retire core Drizzle migration/rekey instructions for switched databases. A PostgreSQL host-journal fixture and isolated fresh path can ship before adoption or mandatory startup enforcement.
