# Adapter-owned core storage migrations

Companions:

The PostgreSQL installer can resolve issue 105 independently of MySQL or a query-layer rewrite. Checkpoints name review boundaries. A checkpoint becomes eligible for release only after its applicable package checks. A test-only future step exercises upgrades without spending a production version. Keep numbered hand-applied scripts, Drizzle development files under `src/database/migrations/`, and new runner assets under adapter-root `migrations/` distinct in code and operator instructions.

## 2. Isolate the PostgreSQL fresh install

**Start with the coexistence fixture.** Extend the CLI's serial database-install integration suite, which already provisions dedicated loopback `*_test` targets through `BYLINE_CLI_POSTGRES_ADMIN_URL`. Give each scenario a fresh named test database and a distinct host object owner. Use the real Drizzle migrator for the host, first with a timestamp above the historical Byline baseline, then with an older unapplied host step after Byline installs. Assert effects in tables as well as journal rows. Run host-first and Byline-first, then advance both independently using a test-only core step against a disposable database. Drive the Byline install in **each order** through the real CLI command with `setup --existing-database` in an isolated host directory. Also run the real dedicated setup path on a fresh target. Build minimal host prerequisites for setup checks, capture exit status and inspect the database independently. Use the CLI entry point for user-visible behavior and the same exported adapter installer directly for concurrency, rollback and fault injection. Capture host ledger rows, owner, ACLs and a sentinel data row around each core operation. Keep synthetic migration input internal to tests; the published API accepts only its embedded manifest.

1. **Adapter.** Freeze the v6.13.4 baseline at native step 0015, add the checksummed manifest and expose `@byline/db-postgres/migrations`. Ship raw SQL relative to the package and validate asset identity before any provisioning. Implement the dedicated/shared fresh installer and transaction executor on a pinned connection. Validate the journal shape and checkpoint digest for retries. Re-inspect after acquiring the bounded core advisory lock. Set a trusted path, qualify the journal and verify the full inventory of created objects. Include the installation identifier, online/fenced classification and monotonic compatibility floor in journal format 1 and the corresponding classification and floor in the manifest. Use fenced/0015 for this baseline. Transactionally create the journal, apply SQL, verify the postconditions and record completion. Return per-step results; on ambiguous commit acknowledgement, inspect before retry.
2. **Preflight.** Derive the claimed names, including implicit row types, constraint indexes, sequences and unprefixed indexes, from the executed baseline. Check relation/type/constraint namespaces and privileges. Add fixtures for a host-only database, a provider-only database, partial core, a wrong-kind journal, a stand-alone type collision, an index collision and an unsupported effective schema. Verify refusal before any persistent change. Exclude no object merely because its name lacks a Byline prefix.
3. **CLI.** Make the switched adapter an exact dependency and load its migrations subpath from the CLI package. Update `db`, `db-init`, setup options, checks and phase detection together. Dedicated init/setup still inspects before provisioning, applies as the app role, retains sticky selection, reset confirmation and seed behavior. The explicit PostgreSQL `setup --existing-database` path consumes the selected connection with driver options intact. It validates flags and endpoint even with saved completed phases, skips admin prompts, role/password changes, database creation, extension creation, grants and ownership changes, and seeds only after successful storage setup. Reject a shared reset and unsupported dialect before any mutation. When checkpoint 2 encounters unjournaled core objects, report the observed objects and refuse setup. Point to the current release-tagged native upgrade guide, explain that this release cannot adopt the installation, and leave the existing schema intact. Introduce the adopt command in diagnostics only when it ships in checkpoint 3. Preserve existing MySQL behavior and asset checks.
4. **Test bootstrap and maintenance.** Route PostgreSQL `migrateTestDatabase` and existing consumers of the `/testing` export through the adapter installer; preserve the `_test` guard. For an old, unjournaled test DB report its state and the existing explicit reset/bootstrap option. Do not auto-adopt or reset it. Keep the core and independent migration journals through cleanup. Isolate shared-host fixtures from broad per-file truncation and verify cleanup leaves their ledger and sentinel data intact. Pin the delegation with a focused import/delegation test: the CLI provisioner loads the adapter migrations export and `test-db.ts` delegates to the function behind that same export. Neither consumer contains a second executor or uses Drizzle's core migrator. Root database initialization provisions the disposable database; the adapter helper installs the core schema.
5. **Release assets.** Update adapter exports/files, CLI dependency and lockfile, selective template copying/sync, artifact check, native history check, PostgreSQL SQL README and installer docs together. Close the legacy stream at 0015 and enforce immutability for the runner baseline, manifest entries and future steps. Keep the existing ownership test on legacy scripts; reject grants, ownership changes, broad guards and transaction-control SQL in the runner stream. Assert a packed CLI resolves the packed adapter's exact entry and bytes in a consumer before host dependencies or config exist. Carry the MySQL CLI baseline until checkpoint 5. Update `RELEASE-INSTRUCTIONS.md` §III at this checkpoint. PostgreSQL release squashes may update only the Drizzle development chain under `src/database/migrations/`. A re-key applies only to a legacy development ledger. Neither operation touches runner assets, switched test databases or a shared host's journal. Keep the unswitched MySQL release procedure.

**Schema changes after the freeze.** A developer updates the Drizzle schema, uses the generated development diff to author a reviewed numbered runner step and immutable manifest entry with classification, compatibility floor and evidence, then compares a fresh runner-built catalog and an upgraded fixture against the intended Drizzle catalog. Exercise any data conversion and writer requirements separately. No PostgreSQL core schema change ships between the checkpoint 2 installer release and checkpoint 4 enforcement. During that window existing dev databases may still use Drizzle's development journal and `drizzle:migrate`; test databases use the runner. Both target the same frozen schema. Introduce the first real post-cutover step only with the startup guard.

**Checkpoint 2 scope.** The cumulative snapshot includes both reviewed planning files, `packages/db-postgres`, `packages/cli`, `pnpm-lock.yaml`, `scripts/check-native-sql-history.mjs` and its test, `RELEASE-INSTRUCTIONS.md`, `docs/01-getting-started/01-cli.md` and the touched development/testing guidance. Include `AGENTS.md` and `knip.exports.baseline.json` if changed. Existing CLI/Vitest CI configuration and the PostgreSQL `/testing` consumer should work through delegation. If verification requires edits to root scripts or `package.json`, `packages/client/tests`, the database bootstrap shell helpers or `.github/workflows/ci.yml`, declare those exact paths in the handoff. Capture every changed path in the run and identify unrelated work separately.

**Acceptance.** Run the new and existing CLI database-install tests, the adapter and CLI unit/typecheck/build gates and the PostgreSQL integration bootstrap. Test two concurrent adapter installers with separate connections: exactly one creates the core schema and baseline row; both reach the same verified version. Inject a failing transactional test step and prove its DDL and journal row both roll back while prior rows survive. Simulate a lost acknowledgement immediately after the baseline commit: the next connection sees the complete schema and exactly one valid baseline row and a retry executes no DDL. Assert a repeat install is a verified no-op; the host still applies its next migration and neither stream advances the other's history. Exercise dedicated refusal, explicit reset on a disposable target, shared setup with no provisioning privileges and seed resumption. Run `pnpm knip`, `pnpm knip:exports` and `pnpm test:scripts` alongside the package gates. The first two are analysis checks (tool caches may change); `pnpm knip:exports:update` rewrites the reviewed baseline and is implementer-only. Script tests use disposable fixtures. Also verify raw packaged SQL parity, legacy ownership protection and a clean artifact resolution outside the workspace. Deliver issue 105's PostgreSQL operator path without activating mandatory journal checks.

## 3. Recognize and adopt existing PostgreSQL databases

**Adapter and CLI.** Implement `storage status`, `adopt` and `migrate` using adapter-root assets without evaluating server configuration. Distinguish empty, host/provider-only, recognized unjournaled core, partial, current, pending, interrupted, newer, corrupt and insufficiently visible. Resolve host adapter metadata from the host root; show CLI-owned version, host version if present, dialect, target database and proposed version. Standalone commands print the CLI-owned version. Refuse skew for mutations unless the operator explicitly supplies the matching target version during a fenced deployment. Resolve missing host dependencies as specified for provisioning versus upgrade.

Build a normalized cutover catalog from fresh **and legacy-upgraded** fixtures. Include columns and defaults, expression/ordering/collation semantics, generated path liveness, constraints, FKs, indexes and both current-version views. Establish the accepted native variants with named fixtures. Compare the historical data predicates from the spec, including source locale, version-locale coverage and legitimate re-anchoring, revision values, publication authorization and deleted-path liveness. Distinguish a valid null file validator from a missing column. For each discrepancy provide a named remediation tested against a representative restore. Keep status and failed adoption read-only. Detect effects of known future core steps without a journal and direct the operator to a verified restore or scoped reversion.

**Acceptance.** Rehearse with representative content, translations, scheduled and versioned documents, admin data and independent host objects. Run the legacy native path in a disposable dedicated fixture with the correct ownership context, then compare its normalized catalog to a clean baseline. Include examples where the latest columns or a Drizzle row are present but required data or constraints are wrong. Reject with the precise discrepancy and an unchanged database. With writers fenced, recheck under lock and atomically add one adopted checkpoint row. A second adoption writes nothing. Upgrade by one synthetic numbered step and compare with fresh-plus-step; verify content and workflow reads and writes, corrupt/gapped/digest-mismatched and future journals, concurrency and lost-ack retry. Test CLI diagnostics for both project-local and standalone invocation.

**Release-phase command.** Add `storage migrate --online-only` using an explicit direct `BYLINE_MIGRATION_DATABASE_URL` and the configured runtime connection. Compare dialect, database and installation identifier, preserve driver options, and require the deployment to pair endpoints correctly. Test wrong database, restored-clone configuration guidance, missing credentials and an unusable session. Do not attempt to certify direct connections from two equal backend PID samples. Report the target release, supported deployed releases, pending classification and the blocked step without printing credentials. The job obtains a bounded lock, rechecks journal integrity and preflights the entire pending set against the deployment inventory. Only an already-current target can succeed without a fleet declaration. A fenced member anywhere, an unproved writer, or an applying/unknown history must leave every step unapplied. The supervised migrate command remains available with a fence.

**Automatic eligibility tests.** Keep production steps fenced until the checkpoint 4 compatibility harness and startup enforcement ship. Use test-only mixed and multi-step manifests to exercise whole-set refusal, concurrent jobs, a successful online sequence and a failure after one step commits. Assert completed rows survive and promotion stops with the appropriate recovery action. Require the repeatable deployed-version argument from actual release inventory; a database journal cannot enumerate long-lived external writers. The release job can populate the argument from deployment metadata. Keep that requirement in the initial design.

## 4. Enforce PostgreSQL compatibility before serving or starting workers

**Core and adapter.** Add the built-in adapter capability and call it before database side effects in `initBylineCore`; inventory worker entry points and use the same guard wherever a worker can bypass initialized core. Retain revision capability/constraint validation and third-party adapter compatibility. Fast startup validates journal shape, contiguous applied sequence, known digests/classifications/floors, supported format and targeted invariants. Newer online rows can admit an older contract only through valid monotonic floors. An unknown fenced row, gap, impossible floor or unsupported format fails readiness. Test an admitted older binary starting after an online step and its refusal after a fenced step. A running legacy writer is controlled by the deployment fence, independently of startup. Keep the deep catalog and content scans in status/adoption. A journal-free transition release may expose the tools while its target remains the frozen checkpoint. Enable mandatory enforcement by the first real post-checkpoint step. Retire legacy Drizzle migrate/rekey entry points and guidance for migrated dev/test deployments as part of this transition, preserving Drizzle development generation.

**Acceptance.** Test a non-owner runtime identity with catalog visibility, schema usage, journal SELECT and normal content DML, with no DDL or journal write privileges. Boot, read and update content at the exact version. Check missing/pending/newer/malformed journals, an incompatible revision constraint and missing named privileges. Assert that no backfill, worker or document operation ran on failure. Verify a split-role runtime account cannot write the journal. Build a harness that installs the real prior release packages and exercises their readers, writers, editorial workflow and workers against intermediate and final schema states. Run earlier releases too if a floor admits them; avoid inferring transitive support. Exercise concurrent old and new writes. Measure and enforce lock/statement budgets under representative table size and contention, including bounded abort. Require this evidence for each online classification. Rehearse operator-led rollout and rollback with old writers fenced. Document independent search/analytics boot-time DDL and the separate privileges required when enabled. Cover the working server bootstrap and worker entry points identified above with integration or focused boot tests.

## 5. Install MySQL with recoverable DDL stages

**Adapter and CLI.** Freeze native checkpoint 0010 with fenced classification, floor 0010 and the same installation-identity contract, and publish `@byline/db-mysql/migrations` with per-stage manifest and raw SQL. Build a database-specific bounded `GET_LOCK` protocol on one session. Preserve the engine check and require effective CHECK enforcement. Preflight names, view definer access, collations and catalog visibility. Commit durable applying intent before the first baseline or upgrade stage, inspect exact before/after predicates at each stage, and mark applied only after all postconditions. Define a verified empty-journal recovery path. Give DML an atomic progress update or a proved idempotent predicate. Retain dedicated-only CLI setup, switch test bootstrap and respect the test suffix. Replace MySQL's CLI template/sync gate with its corresponding packed adapter gate; close legacy SQL at 0010.

**Acceptance.** Use MySQL 8.0 on disposable `_test` targets. Inject failures after journal creation, after recording intent, between two committed DDL statements, and between final DDL and the journal update. Reconnect with a new physical connection; verify exact stage diagnosis, safe resume and a single completed row. Change one object's definition to an incompatible shape and assert repeated diagnosis without mutation. Test double install, lock contention, timeout and restricted holder visibility. Verify dedicated seed/refusal/reset behavior, cleanup that preserves history, and package resolution before host config can load.

## 6. Adopt and upgrade MySQL; enforce startup

**Adapter, CLI and core.** Add MySQL's normalized adoption evidence, explicit upgrades, non-owner runtime checks and the phased enforcement rule established for PostgreSQL. Exercise MySQL-specific generated columns, sign/width/defaults, ordered unique keys, FK/check enforcement, definer views, migration data predicates and valid historical shapes. Close the hand-applied stream with versioned remediation instructions. Keep production SQL immutable.

**Acceptance.** Test fresh versus native-upgraded equivalence, failed and repeated adoption, journal corruption or newer schemas, pending and interrupted upgrades, startup and normal content operations as a DML-only account. Deep inspection must explain missing metadata privileges including SHOW VIEW. Verify application startup cannot pass with an applying row, including when the final DDL is already visible. Implement release-phase-only online automation with the same direct/runtime identity and complete pending-set checks. Require the prior release suite to pass at each durable MySQL DDL prefix. Check enforced algorithm and lock limits, test a server refusing the requested online algorithm, and interrupt after the last DDL before journal completion. A subsequent automatic job must refuse an applying row; only supervised recovery can complete it. Exercise readiness loss for new instances during interruption and document deployment capacity requirements. Rehearse scoped repair or fenced restore on the ambiguous DDL fixture. Ship the new startup requirement only after the adoption procedure is available to deployments.

## 7. Verify release packages and rehearse deployment

**Release tooling, CI and docs.** Extend the current CLI tarball and native SQL history gates per switched dialect. Keep SQL and schema-definition changes synchronized by comparing a fresh runner-built catalog to the intended Drizzle schema and a representative upgraded database. Reject edits, deletions, renumbering, digest drift, missing raw SQL and unmanifested steps. Ensure append-only manifests permit new entries while freezing old ones. Update public CLI, setup, local testing, rollback and release instructions and checked references such as AGENTS.md at the applicable cutover. Include a supervised PostgreSQL raw-SQL procedure with the same preflight, schema pinning, transaction, fencing and explicit post-install adoption.

Install locally packed release-form dependencies in a clean consumer that cannot reach workspace sources or substitute registry versions of the packages under test. Cover both CLI-first setup and an existing host with exact or skewed versions. Exercise status, install, adoption, pending migration, startup and sample content/workflow operations against isolated databases. Compare host Drizzle journals, unrelated rows and owners before and after, and verify search/analytics advance independently. Test missing/corrupt package assets fail before provisioning. Add a generic release-job and one-shot pre-start recipe: resolve active release versions from deployment inventory, provide a direct DDL identity exclusively to that job, keep the application on runtime credentials, and promote only after exit zero. Exercise `--online-only` from the packed consumer against a proven online step and a blocked mixed set on each switched engine before releasing the automatic feature. Show which journal rows survive a mid-run failure and how to stop or resume with supervision. A disposable database copy can rehearse a release using its own paired endpoints. Include this per-dialect smoke in its first applicable release gate and run the full two-dialect matrix once both switch.

**Acceptance.** Demonstrate fresh and upgraded target schemas converge, the published CLI resolves the matched adapter and raw SQL before server config loads, and ordinary runtime credentials can start the application. Supply a restore rehearsal on isolated data showing the code and core schema roll back together where required, with the host recovery point accounted for. Operational rollout, releases and branch commits require separate instruction.

## Verification and handoffs

Run targeted node tests and package typechecks/builds for each affected owner. Integration suites run serially; keep the repository's one-worker settings. For checkpoint 2 use `pnpm --filter @byline/cli exec vitest run --mode=integration tests/database-install.integration.test.ts` and the targeted PostgreSQL adapter suites; a separate coexistence fixture in the same directory must also be selected if split out. Later include client/core boot tests and full serial integration as appropriate. Run `pnpm docs:check` and `git diff --check` after documentation updates. The docs checker covers `docs/`; review spec/plan links and examples separately.

Each implementation handoff supplies the cumulative changed paths, stable snapshot and both manifests; exact commands, outcomes, assertion names for ordering/concurrency, actual test database names and server versions; and any skipped checks. Source-rewriting commands such as `pnpm lint`, code generation and full host builds are implementer-only. Package builds/tests can write caches and dist; integration and DB bootstrap mutate isolated test databases. Verify the approved snapshot before dependent work. Pause after checkpoint 1 until the operator explicitly restarts implementation.
